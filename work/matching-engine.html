Matching Engine

A price-time priority limit order book in C++20, fuzzed against a reference model, with a NASDAQ ITCH 5.0 feed handler and a live demo that runs in your browser.

A matching engine is the core of an exchange: it holds the order book and decides who trades with whom. This one is a price-time priority limit order book in C++20, header-only, with no allocation on the request path, plus a NASDAQ TotalView-ITCH 5.0 feed handler built on the same books. It’s checked against a reference model rather than just tested, and benchmarked rather than described as fast. It also runs in your browser: the engine is compiled to WebAssembly, so you can trade against live synthetic flow and watch your place in the queue move.

What it does

  • Limit, immediate-or-cancel, fill-or-kill, market and post-only orders. Fills print at the resting order’s price, so an aggressor gets any price improvement.
  • Cancel and cancel/replace with exchange queue rules: shrinking an order keeps its place, growing it or moving its price sends it to the back.
  • Self-trade prevention that cancels the resting order, the incoming one, or both, and a fill-or-kill check that applies the same rules.
  • Risk checks for prices outside a band, zero quantities, duplicate ids and a full book, with execution reports and a market-by-price feed out.

Design

Orders live in one preallocated pool of 40-byte slots, linked into a first-in, first-out queue at each price: matching takes from the head, new orders join the tail, and a cancel unlinks in constant time. Finding an order by id uses an open-addressing hash table with Fibonacci hashing, kept at most half full. It deletes by shifting entries back instead of leaving tombstones, so a cancel-heavy flow never degrades it and it never needs a rehash, which would be a latency spike.

Price levels are a flat array per side indexed by tick, and a 64-way hierarchical bitset finds the next populated level after the best one empties, reading at most two words per layer. Events reach the caller through a template parameter, so every callback inlines: there are no virtual calls, locks, exceptions or allocations while a request is processed. The storage is a pluggable policy, which is how the benchmark compares designs on identical order flow.

Proving it’s right

Fast and wrong is easy, so most of the testing goes into correctness. A separate reference book, built on std::map and std::list and sharing no code with the real one, is an executable specification of the matching rules. Two of its rules are deliberately written differently, so the two implementations can’t share a mistake. Both books get the same random request stream, including every order type, duplicate and unknown ids, cancels racing fills and a pool small enough to fill up, and after every request their event streams must be identical. A soak run of 36 million requests found no differences.

Around that sit 287 GoogleTest tests, each run against all three storage policies; a mutation check that injects eight plausible bugs and confirms the suite catches every one; and AddressSanitizer, UndefinedBehaviorSanitizer and ThreadSanitizer runs in CI, with warnings as errors on GCC, Clang and Apple Clang.

How fast

Each workload is generated once by a deterministic flow model, a random-walking price with liquidity thickest near the touch, and replayed five times on a fresh book. Every design has to produce bit-identical trades, checked through a running hash, so a faster but wrong one fails the run.

One core, requests per second. The M2’s timer ticks every 41.67 ns, so its percentiles are upper bounds.

With a million resting orders the book no longer fits in cache, and a cancel becomes a chain of dependent cache misses. A batched replay hides them with a software pipeline: while request i runs, it is already fetching the index slot for request i+16, the order for i+10, and its queue neighbours for i+4. That costs about a third of throughput while the book is small and wins 50–79% at a million orders, so the engine measures the book every 1,024 requests and only prefetches above 262,144 resting orders.

It also runs as a service: a gateway thread, the engine and a drop-copy thread connected by lock-free single-producer, single-consumer rings. Latency is charged from each request’s scheduled send time, so a stall can’t hide by delaying the requests behind it. Publishing once per batch instead of once per request raised the M2’s sustainable rate from 2M to 5M requests a second; the EPYC sustains 10M at a 0.21 µs median.

A real NASDAQ trading day

The books also run in reverse. The ITCH 5.0 feed handler rebuilds every instrument’s book from NASDAQ’s public order-by-order feed, mirroring rather than re-matching it, since real books lock and cross during auctions and halts. On the full session of 30 January 2019, 368,366,634 messages across 8,714 instruments, every order reference resolved, every book ended the day empty, and during continuous trading 100% of executions hit the best price and 99.91% hit the front of the queue, as NASDAQ’s price-time rules require. The whole day replays in 25.5 seconds on one M2 Pro core.

Limits

Each book runs on one thread by design, since matching is sequential per instrument; scaling comes from sharding symbols across threads. There’s no FIX or OUCH gateway, journal or recovery, the fast price array needs a bounded price band, and the ITCH handler has been run on one real day and rebuilds NASDAQ’s displayed books only.
